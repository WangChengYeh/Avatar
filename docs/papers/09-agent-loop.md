## 1　問題

執行者是對話式的 AI，跑在各自的沙盒裡（ChatGPT 在 Codex 環境，Gemini 在 Antigravity）。它們有三個特性，讓「照 SOP 做」沒有想像中簡單：

1. **不會主動問，也不該停下來問。** 停下來就要人去叫它繼續。
2. **只照明確的指示做。** Claude 在 issue 裡的留言它們不會照做；它們只照 `next_step.py` 的輸出與修圖單。
3. **一個指令跑太久會被沙盒砍掉**，而且時限沒有公布。

所以每一輪結束時，「接下來做什麼」必須由程式根據結果算出來，並且寫成一個可以直接執行的指令。

## 2　理論

### 2.1　狀態機

每一輪跑完 `run_all.py` 之後，執行者執行 `next_step.py`。它是一個函數：輸入是這個 avatar 的歷史（每一輪的四關結果、程式指紋、登記的 issue），輸出是八種狀態之一。

| 狀態 | 意思 | 執行者做什麼 |
| --- | --- | --- |
| START | 還沒有任何結果 | 生圖、跑流程 |
| RUN | 有照片，但結果不是這一版程式算的 | 同一組照片開新版本重跑 |
| RETOUCH | 診斷追到指名的照片 | 照 AI 修圖單重畫那幾張，再跑 |
| CODE | 診斷追到程式，且有改 code 單 | 照單修改 |
| ESCALATE | 自己修不了 | 發 issue 給 Claude，登記編號 |
| WAITING | 已發 issue，程式還沒變 | 等（見 2.4） |
| UPDATE | main 上有新的程式 | `git pull`，再執行一次 next_step |
| DONE | 四關 0 FAIL | 交付 |

只有 DONE 可以停。這個函數是「跑一次回一次」，沒有任何東西在背景輪詢；迴圈靠執行者一再呼叫它來轉動。函數漏掉一種情況，迴圈就停在那裡。

### 2.2　什麼叫有進步

RETOUCH 與 ESCALATE 的分界是全篇的核心：重畫是便宜的，但如果問題其實在檢查或門檻，重畫一百輪也沒用。

把一輪的結果記成 $$(g,\ F)$$：$$g$$ 是跑到第幾關，$$F$$ 是那一關 FAIL 的項目集合。定義第 $$b$$ 輪相對第 $$a$$ 輪**有進步**：

$$
\operatorname{progressed}(a,b)\iff
\begin{cases}
g_b>g_a, & g_a\ne g_b\\[2pt]
\lvert F_b\rvert<\lvert F_a\rvert, & g_a=g_b
\end{cases}
$$

也就是對 $$(g,\,-\lvert F\rvert)$$ 做字典序比較：先比關卡，同一關再比 FAIL 項數。先比關卡是必要的：第 2 關 3 項 FAIL 退到第 1 關 1 項 FAIL，項數變少，卻是退步。

**卡住**的項目 $$\operatorname{stuck}$$ 是下面兩者之一（只算同一版程式跑的輪次）：

$$
\bigcap_{r\in\text{最近 5 輪}}F_r\ne\varnothing
\qquad\text{或}\qquad
\Bigl(\text{最近 2 次重畫都沒有進步}\ \wedge\ \bigcap_{r\in\text{最近 3 輪}}F_r\ne\varnothing\Bigr).
$$

第二個條件抓「重畫沒用」；第一個是保險：就算每輪都少一項，同一項拖了 5 輪也該有人來看。

這個定義依賴 $$F$$ 裡的項目名稱在兩輪之間可以比對。名稱裡若混進量測值（「頭部特寫相鄰一致：10.3」），兩輪永遠不相同，交集永遠是空的，卡住的條件永遠不成立。

### 2.3　程式指紋

「這個結果還算數嗎？」與「Claude 修好了嗎？」是兩個不同的問題，用兩個指紋回答：

| 指紋 | 包含 | 用途 |
| --- | --- | --- |
| 結果指紋 | 產生結果的程式（重建、檢查、診斷），**不含** `next_step.py`、`escalate.py`、`data_repo.py` | 結果指紋變了 → RUN：同一組照片重跑。只改文件或控制程式不重跑 |
| 控制指紋 | `body3d/` 全部 | 登記等待時記下；之後任何變動 → 不再等 |

另外，「同一個 FAIL 幾輪」只在同一個結果指紋內計數：程式換了，新的 SOP 先給一次重畫的機會。

用指紋而不用 issue 狀態，是因為 issue 要等執行者回報後才由 Claude 關閉；若等待的結束條件是「issue 關閉」，兩邊就互等（第 3 節第 1 列）。

### 2.4　時限未知時怎麼等

WAITING 時要有東西定期檢查 GitHub。執行者自己不會定時醒來，所以由程式在一個指令內等：`next_step.py --wait` 每 60 秒檢查一次，狀態一變就回來。問題是一個指令能跑多久。

設沙盒在指令執行 $$L$$ 秒時把它砍掉，$$L$$ 未知。每一段等待先寫心跳檔（開始時間、最近一次心跳、預算、是否完成）。下一段開始時讀它：

- 上一段寫了「完成」而且等滿了預算 $$b$$：沒被砍，$$L>b$$。下一段 $$b\leftarrow\min(1200,\ 1.5\,b)$$。
- 上一段沒寫「完成」：被砍了。它最後一次心跳在 $$\tau$$ 秒，所以 $$\tau\le L<\tau+60$$。記下 $$\tau_{\min}=\min(\tau_{\min},\tau)$$，之後

$$
b=\operatorname{clamp}\bigl(60,\ 1200,\ \min(b,\ 0.7\,\tau_{\min})\bigr).
$$

第一段 $$b=300$$ 秒。係數的理由：

| 參數 | 值 | 理由 |
| --- | --- | --- |
| 第一段 | 5 分 | 觀察到一個 7 分鐘的指令在 ChatGPT 的環境沒被砍 |
| 成長 | × 1.5 | 用少數幾段就接近時限，又不會一次跳過太多 |
| 上限 | 20 分 | 社群回報整個任務約 25 分鐘被切（非官方） |
| 被砍後 | × 0.7 | $$L$$ 可能逐次不同（負載）；留 30% 餘裕 |
| 下限 | 1 分 | 比檢查間隔短就沒有意義 |
| $$\tau<60$$ 秒的中斷 | 不算 | 幾秒內被中斷多半是人按了停止，不是時限；否則預算會被釘在下限 |

被砍一次的代價是那一段白等，之後就不會再被砍。這和網路壅塞控制的想法相同（沒有壅塞就加大、遇到就縮小），差別是這裡縮小的依據是直接量到的 $$\tau$$。

同樣的道理用在重建本身：`progress.json` 停在「執行中」超過 30 分鐘沒有更新（每一步開始與結束都會寫，最長的一步只有幾分鐘），就判定被砍，回 RUN。

## 3　九次卡死

| 現象 | 原因 | 修正 |
| --- | --- | --- |
| R33 停在 WAITING，Claude 已經合併修正 | 結束等待的條件是 issue 關閉；issue 要執行者回報後才關；執行者的 `gh` 沒登入，查不到狀態。兩邊互等 | 等待改看程式指紋；issue 不必先關 |
| R33–R41 同一個 FAIL 重畫了 8 輪，沒有發 issue | ESCALATE 的步驟是 `gh issue create`，做不到，就繼續重畫 | 沒有 `gh` 時改用 GitHub 連結器發；發不了也不准再重畫 |
| R48 用與 R47 完全相同的照片在新程式上重跑，立刻被判「修了 2 輪」 | 計數跨越了程式版本 | 只算同一個結果指紋的輪次 |
| ChatGPT 每輪都在變好，卻每隔一輪就發 issue | 舊規則：同一項在連續 2 次執行都出現就升級。只重畫一次就算 2 輪；7 張修好 5 張也算沒修好 | 2.2 的進步定義 |
| R55–R61 在第 2 關修了五輪，從未升級 | 項目名稱用半形冒號切，烘焙前檢查用全形「：」，名稱裡帶著量測值，前後兩輪永遠不相同 | 兩種冒號都切 |
| 6 組特寫不一致，修圖單只點名 4 張，修了三輪還有 3–7 組 | 只列「出現在兩組裡」的照片 | 5 組以上就列整圈 8 張，一次重畫 |
| 一天合併 10 次，每次所有 avatar 都重跑一遍，數字完全相同 | UPDATE 一律要求重跑，包括只改文件的合併 | 2.3 的結果指紋 |
| WAITING 印「可以停下來」，之後沒有人再檢查 | 函數跑一次回一次，沒有輪詢 | `--wait`（2.4） |
| 重建跑到一半被砍，next_step 永遠回「還在跑」 | `progress.json` 停在執行中 | 30 分鐘沒更新就判定中斷 |

每一列都是狀態機少了一條邊，或邊上的條件永遠不成立。沒有一列是執行者「不聽話」：它們都照著當時的輸出做了。

### 4.2　兩個執行者用版本的方式不同

從雲端硬碟上各版第 1 關結果包（33 張照片的壓縮檔）的大小判斷照片有沒有換：

| | ChatGPT avatar_001 | Gemini avatar_001 |
| --- | --- | --- |
| 版本範圍（當時） | v033–v054 | v002–v009 |
| 照片 | 幾乎每一版都不同（29.5–32.5 MB，各版不同）；只有 v048 與 v049 完全相同 | v002–v008 是同一組（大小只差幾個位元組）；v009 才換 |
| 每一版代表 | 重畫了一輪照片 | 多半是換了程式重跑 |
| 多數版本停在 | 第 1 關 | 跑完四關 |

兩種用法都符合「重畫或重跑都開新版本」的規則，但含義不同：ChatGPT 的版本號是照片的修訂數，Gemini 的版本號接近程式的版本數。2.2 的進步定義與 2.3 的指紋要對兩種用法都正確：對 Gemini，換程式重跑不能算「重畫沒進步」；對 ChatGPT，小幅重畫有進步就不該升級。

### 4.3　升級規則改變前後

| 情境 | 舊規則（連續 2 次出現就升級） | 現行規則 |
| --- | --- | --- |
| 7 項 FAIL → 重畫 → 3 項（同一關） | 升級 | 繼續修（有進步） |
| 第 1 關 FAIL → 重畫 → 到第 2 關才 FAIL | 不升級（項目不同） | 繼續修（關卡前進） |
| 第 2 關 3 項 → 重畫 → 第 1 關 1 項 | 2.21.0 的初版只比項數，算成有進步 | 不算進步（先比關卡） |
| 同一項，重畫 2 次都沒進步 | 第 2 次執行就升級 | 第 3 次執行升級 |
| 同一項拖了 5 輪，每輪都少一點 | — | 升級 |

## 5　討論與限制

- **程式只能在一個指令裡等。** 執行者整個回合被平台結束之後，仍然要人或排程對它說「繼續」。等待期間持續消耗執行者的用量。
- **留言不是指令。** ChatGPT 在 issue 回報了項目名稱比對的錯，Claude 之後在同一個 issue 留言 8 次都沒有讀到它，隔天才修。反過來，Claude 的留言執行者也不會照做。兩個方向的結論相同：要對方做的事必須進到它一定會讀的地方。對執行者是檢查與修圖單；對 Claude 是「處理 issue 前先讀執行者的留言」，已寫進交接清單。
- **進步的定義只看項數。** 一項由 FAIL 很多變成 FAIL 一點點，項數沒變，不算進步；可能過早升級。
- **人的角色。** 會改變程式行為的 PR 等人說合併；只改文件或測試的由 Claude 自己合併。這一條不是技術限制，是責任的劃分。

## 6　重現

```sh
python body3d/next_step.py ./output             # 印出狀態與下一步，寫入 next_step.md
python body3d/next_step.py ./output --wait      # 等 Claude 時：在時限前回來，印出要再執行的指令
python -m pytest -q tests/test_next_step.py tests/test_escalate.py
```
