# Loop engineering 的理論基礎

[返回 README](../README.md#loop-engineering) · [流程與驗收](Workflow-and-Validation.md) · [版本與量測紀錄](../CHANGELOG.md)

README 的 Loop engineering 寫的是「怎麼做」。本文說明這些步驟背後「為什麼」，以及每條規則對應到哪段程式。

## 前提：一個不動的虛擬人物，被一台假想相機環繞拍攝

人物是 AI 根據一張原始照片生成的虛擬人物。33 張圖是 AI 假想「人物擺好 T-pose 完全不動，相機繞著他拍」所畫出來的：

| 組別 | 假想相機位置 |
| --- | --- |
| 水平全身 | 水平 8 個角度 |
| 俯角 30° 全身 | 俯角 30°、8 個角度 |
| 仰角 20° 全身 | 仰角 20°、8 個角度 |
| 頭部特寫 | 水平 8 個角度，近拍頭部 |
| 正上方 | 1 張 |

重建要解三組未知數：人物形狀（網格）、表面顏色（貼圖）、每張圖的相機。已知條件只有一條：**每張圖都是「同一個不動的人 × 某一台相機」的正交投影。**

因為人物不動，同一個身體點從任何角度看都必須同時滿足：

| 一致性 | 意思 | 對應的檢查 |
| --- | --- | --- |
| 剪影一致 | 模型投影到每張圖，輪廓與圖吻合 | `check_turnaround.py` 第 10 項紅藍圖、`fit_report.py` |
| 位置一致 | 同一特徵點（鼻尖、耳緣、指尖）在各圖的位置，可用同一個 3D 點加各自相機解釋 | 第 10b、11 項，`steps/face33.py` 的三角量測 |
| 顏色一致 | 同一塊皮膚在各圖顏色相同 | 曝光、臉頰亮度、烘焙前頭部檢查的亮度差 P90 |

## 推論一：對不上，就一定有一方錯了

虛擬人物不會呼吸、不會移動，光線、曝光、相機都能在生成提示詞裡指定。兩張圖對不上時，錯誤來源只剩兩種：

| 錯誤來源 | 例子 | 修哪裡 |
| --- | --- | --- |
| **AI 畫得不一致**（最常見） | 3/4 特寫的臉相對頭髮畫大 13–16%；耳朵在 45°／90°／135° 位置不同；俯角圖帶透視 | 先讓 checker 能抓到，再重新生成那幾張 |
| **程式估錯或放大誤差** | 90° 頭部特寫對成 107°；外殼投票在兩腿間留下殘條；烘焙把錯開的兩張圖混成重影 | 最早出現差異的那一步 |

真人拍攝要考慮的呼吸、姿勢漂移、鏡頭透視、光線變化，在這裡都不存在。

## 推論二：重建無法消除不一致，只能決定誰說了算

輸入不一致時，烘焙只有兩種選擇：

- **平均**：多張錯開的圖疊在一起 → 重影（臉兩層、耳後第二條輪廓）。
- **挑一張**：讓某張圖獨佔 → 不同圖的交界處出現接縫。

`steps/bake33.py` 的權重（主環 ×6、`head_000deg` ×6、指數 `PW=12`）就是在兩者之間取捨。Issue #17 的兩次試修正好碰到兩邊：加重 90° 特寫減輕重影，卻在後斜面多出髮色接縫；縮小耳區加漸變後才都能接受。

因此程式端的修正只是**緩解**，真正的**根治**是讓輸入一致。

## 推論三：checker 是給 AI 的規格書

- **門檻從完美輸入校準。** 用模型渲染、相機已知的合成照片量出程式本身能達到的誤差，再加一點餘量。FAIL 的意思是「比理想輸入還差」，問題在圖。
- **AI 模式從嚴。** 重新生成的成本很低，AI 理論上能畫到完全一致，所以不合格就重畫，不讓程式去遷就。`--mode photo` 的較寬門檻是為真實照片保留的，本情境用不到。
- **透視要擋掉，而不是去適應。** 提示詞可以要求正交投影與長焦，圖中出現透視代表 AI 沒照規格畫，應由第 10b 項 FAIL 後重畫。2.3.0 起程式能估計俯角／仰角環的相機距離，是讓不合格照片也能先重建的權宜做法。
- **固定的拍攝規格本身就是約束。** 檔名就是相機位置。只靠剪影分不開俯仰角、距離與縮放，所以照片檢查通過時，相機只允許偏離檔名角度 ±3°（`steps/camera.py`、`work/check_status.json`）。

## 推論四：以原始照片為錨點

虛擬人物沒有真實 3D 形狀可以對照，唯一的基準是原始照片，以及最接近它的正面圖（`01_000deg`、`head_000deg`）。其他角度都要與錨點一致，不一致就重畫那一張。

- `steps/face33.py` 以 `head_000deg` 為錨，把 3/4 特寫的相機對過去，並以它的視線方向量測五官深度。
- 耳部這類側面特徵，以 90°／270° 側面為錨，比對 45°、135°、225°、315°。

## 推論五：差異第一次出現的那一步，才是病因

重建是一條管線：照片 → 相機 → 網格 → UV／烘焙 → 骨架權重 → GLB 匯出 → Three.js。沿管線逐步比較，找出第一個與原圖不符的步驟，就像二分法除錯。

- **先統一比較條件。** 模型擺回 T-pose，用原圖的校準相機、裁切與尺度渲染（[`compare_turnaround.mjs`](https://github.com/WangChengYeh/Avatar/blob/157ece784724c998054adf631623262933ff0e96/scripts/compare_turnaround.mjs)，尚未合併進 main；回投疊圖；`fit_report.py`）。否則看到的只是視角或投影不同。
- **用開關做差分測試。** Issue #17 關閉貼圖後重影消失，可確定差異出在烘焙，而非網格。
- **先比圖與圖，再比圖與模型。** 同角度全身照對頭部特寫、跨角度回投到同一視角；圖之間已不一致，就屬於推論一的第一類。

## 推論六：先有檢查，再修正，檢查只增不減

- 新規則先在**未修正的圖**上 FAIL（證明抓得到），在**合成對齊的控制組**上 PASS（證明不誤報）。
- 修正後該項由 FAIL 轉 PASS，其他角度與既有規則沒有新增 FAIL。
- 修程式也一樣，同時加入能重現問題的檢查，例如 `verify_glb.py` 的頭部黑條偵測、擺姿勢三角形邊拉長檢查。
- 檢查留在 repo 裡、接進 `run_all.py`（照片檢查、烘焙前頭部檢查、GLB 驗證任一 FAIL 就停），同一個問題下次會被自動擋下。`--force` 只是診斷用的逃生口。

## 推論七：在相同條件下驗收，一輪一個 Issue

- 驗收使用相同指令、門檻、角度與相機，從新的輸出目錄重建、不加 `--force`，避免讀到舊的中間檔。
- 一個 Issue 記錄一輪「觀察 → 假設 → 試修 → 驗收」。每個判斷都附量測與圖，可追溯；關閉代表驗收通過；下一輪開新 Issue 並連回上一輪。

## 程式誤差分開量

照片的一致性由 checker 負責；程式本身的誤差用相機已知的合成照片另外量（`body3d/camera_benchmark.py`、`fit_report.py`）。兩者分開，才知道一個 FAIL 該重畫圖還是修程式。

## 範例：Issue #17 耳部重影

| 步驟 | 對應推論 | 狀態 |
| --- | --- | --- |
| 關閉貼圖後重影消失 → 差異在烘焙 | 五 | 完成 |
| 45°／90°／135° 特寫回投到 90°，耳緣位置不同 → AI 畫得不一致 | 一、四 | 完成 |
| 新增耳部特徵點檢查，原圖 FAIL、合成控制組 PASS | 六 | 僅在作者本機，尚未進 repo |
| 調整烘焙權重，重影消失 | 二（緩解） | 完成，v1230 |
| 以 90°／270° 為錨，重新生成偏差大的圖，讓耳部檢查 PASS | 三、四（根治） | 未做 |
| 135°／225° 頭部看起來比模型更接近正側面：先查是圖畫錯還是相機估錯 | 一、五 | 待追查 |

完整的一輪應補上耳部檢查進 repo，並在原圖上由 FAIL 轉 PASS。
